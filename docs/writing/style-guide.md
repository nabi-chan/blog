# 은솔 문체 가이드

`/write-post`, `/refine-post` 가 따르는 한국어 글 규칙이다. 은솔의 예전 글 12편(약 1만 자)을 분석해서 만들었다. 은솔이 고쳐 주면 이 문서를 고친다. 영어 번역 규칙은 `.claude/commands/translate-post.md` 에 있다.

## 1. 어조

- 모든 문장은 **합니다체**로 쓴다. 독자에게 말을 거는 문장과 괄호 안의 보충에도 해요체·해라체를 섞지 않는다.
  - 좋음: "캐시는 하루가 지나면 지웁니다. 설정에서 바꿀 수도 있습니다."
  - 나쁨: "캐시는 하루가 지나면 지웁니다. (설정에서 바꿀 수도 있어요)"
  - 나쁨: "캐시는 하루가 지나면 지운다. 설정에서 바꿀 수도 있다."
- 괄호에는 독자에게 보여 줄 것만 넣는다: 원어 병기, 짧은 보충.
  - 괄호 안에 완결된 문장이 둘 이상이면 문단으로 풀어 쓴다.
- 현재까지 계속하고 있는 행동은 진행형으로 쓴다.
  - 좋음: "할 일에 알림을 달 수 있어서 리마인더로 쓰고 있습니다."
  - 나쁨: "할 일에 알림을 달 수 있어서 리마인더로 씁니다."
- 행동의 주체를 명시한다. 사람과 AI가 함께 등장하는 글에서는 주체가 모호해지기 쉽다.
  - 좋음: "잘못 묶으면 Slack에서 제가 정정합니다."
  - 나쁨: "잘못 묶으면 Slack에서 말로 고칩니다."
  - 단, 절의 소제목이나 앞 문장에서 주체가 이미 분명하면 되풀이하지 않는다. 글쓴이가 하는 일을 나열하는 절에서는 "제가"를 문장마다 쓰지 않는다.
- 1인칭은 "저/제"다.
- 기술 글에도 소감이나 동기를 한 줄은 넣는다. 단, **은솔이 실제로 말한 것만** 쓴다. 지어내지 않는다.
- 유머는 짧은 반전, 말줄임, 가벼운 감탄사로 낸다.

## 2. 구조

### 시작

- 기술 글은 인사 없이 `## X?` 정의 섹션으로 시작한다.
  - 첫 문장은 "X는 ~입니다."로 쓴다.
    - 좋음: `## D1?` → "D1은 Cloudflare가 제공하는 SQLite 기반 데이터베이스입니다."
  - 정의 다음 문단에는 글을 쓴 목적과, 독자가 글을 읽은 뒤 얻는 것을 쓴다.
    - 좋음: "이 글은 Hermes Agent를 이렇게도 쓸 수 있다는 것을 공유하려고 썼습니다."
    - 대상 독자는 편집 메모에서 정하며, 본문에 "~한 분을 위해 썼습니다", "~한 분을 생각하며 썼습니다"와 같이 별도로 밝히지 않는다.
- 조사기(아래)는 `## X?` 대신 무엇이 어떻게 안 됐는지로 시작한다.
- 개념은 쓰이기 전에 정의하고, 배경 설명은 처음 필요한 자리까지 미룬다.
  - 아직 소개하지 않은 대상을 앞에서 언급해야 하면 "뒤에 소개할 X"와 같이 뒤에서 설명한다는 사실을 밝힌다.

### 흐름

- 소제목은 독자가 품을 질문의 순서대로 놓는다.
- 문단 하나에는 요지 하나만 둔다. 요지는 첫 문장에 두고, 나머지 문장은 근거·예시·한계를 맡는다.
- 문장은 대부분 60자 이내, 문단은 1~3문장이다. 강조할 한 문장은 따로 뗀다.
- 같은 대상을 설명하는 짧은 문단이 연속되면 3문장 이내의 한 문단으로 합친다.
- 앞 문장이 뒤 문장의 원인이나 조건이 되는 짧은 문장 둘은 연결 어미(-어서, -어, -으면)로 이어 한 문장으로 쓴다. "그때는", "그래서", "그러면"으로 시작하는 뒤 문장은 앞 문장에 붙인다. 합친 문장이 60자를 크게 넘으면 두 문장으로 두되 접속사는 뺀다.
  - 좋음: "자동으로 묶다보니 틀릴 때가 있어 Slack에서 하나씩 정정해야 합니다."
  - 나쁨: "자동으로 묶다 보니 틀릴 때가 있습니다. 그때는 제가 Slack에서 하나씩 정정해야 합니다."
- 뒤 문장이 앞 문장을 뒤집는 역접(할 수 있다 → 할 수 없다, 된다 → 안 된다)은 접속사로 드러낸다. 짧으면 "-지만"으로 한 문장에 잇고, 합치면 60자를 넘을 때는 두 문장으로 두고 사이에 "그러나"를 둔다. 접속사를 빼는 규칙(5절)은 원인·순접에만 적용한다.
  - 좋음: "Hermes Agent는 시키면 Gmail을 검색하고 읽을 수 있습니다. 그러나 새 메일이 왔을 때 스스로 깨어나 읽지는 못합니다."
  - 나쁨: "Hermes Agent는 시키면 Gmail을 검색하고 읽을 수 있습니다. 새 메일이 왔을 때 스스로 깨어나 읽지는 못합니다."
- 한 절에는 그 절의 소제목에 속하는 내용만 둔다. 소제목과 맞지 않는 문단은 해당 내용을 다루는 절로 옮기거나 삭제한다.
  - 예: "직접 만든 도구" 절에 직접 만들지 않은 외부 서비스 설명을 두지 않는다.
- 하나의 사실은 한 곳에서 설명한다. 사용 장면 목록과 상세 설명처럼 같은 사실이 두 절에 걸쳐 나와야 하면, 뒤쪽은 앞을 받는 문장으로 쓰고 같은 문장을 되풀이하지 않는다.
  - 좋음: "하루에 세 번 받는 할 일 정리도 Structured에 쌓인 할 일로 만듭니다."
  - 나쁨: 앞 절의 "10시, 17시, 22시에 할 일을 정리해서 보냅니다."를 뒤 절에서 그대로 반복
- 가벼운 내용에서 본론으로 넘어가는 절 사이에는 전환 문장을 한 문장 둔다. 목록 바로 다음에 어조가 다른 소제목을 붙이지 않는다.
  - 전환 문장도 사실을 담는 문장이다. 연결을 위해 만든 문장이라도 그 내용이 사실인지 확인한 뒤에 쓴다. 확인하지 못한 사실은 쓰지 않고, 확인할 수 있는 사실로 바꾸어 쓴다.
    - 좋음: "이런 일은 이로하에게 말로 시키면 되지만, 통화와 메일은 달랐습니다."
    - 나쁨: "이런 일은 Hermes Agent가 기본으로 갖춘 기능만으로도 됩니다." (별도 스킬이 필요한 작업이 포함되어 있었다)
- 한 문장이 여러 절로 이루어지면 각 절의 주체를 맞춘다. 앞 절의 주체가 AI이면 뒤 절도 AI를 주체로 쓰고, 주체가 바뀌면 문장을 나눈다.
  - 좋음: "여러 단계를 거쳐 일을 해냈거나, 막혔다가 길을 찾았거나, 사용자가 방식을 고쳐 주면"
  - 나쁨: "여러 단계를 거쳐 일을 해냈거나, 막혔다가 길을 찾았거나, 제가 방식을 고쳐 주면"
  - 예: "X는 ~입니다." 문단과 "X는 ~에서 동작합니다." 문단은 하나의 문단으로 쓴다.
- 직접 만든 것을 소개할 때는 정의 → 필요했던 이유(당면한 문제) → 문제를 해결하기 위해 만든 것의 순서를 따른다. 제시한 문제와 해결책은 서로 대응해야 한다.
- 도구나 비서를 소개할 때는 기능 목록보다 실제 사용 장면을 먼저 제시한다. 하루의 흐름, 실제로 하는 질문과 그에 대한 응답을 구체적으로 쓴다.
- AI에게 맡기는 작업은 작업 내용과 함께 수행 수단과 결과물을 명시한다.
  - 좋음: "지도 API를 사용해서 목적지까지 가는 시간과 경로를 계산해주기도 하고"
  - 좋음: "중고 매물을 찾아 원하는 매물이 나왔는지 보고하거나"
  - 나쁨: "중고 매물을 찾아 줍니다."

### 생략할 세부 사항

초고를 완성한 뒤 각 문장을 삭제했을 때 독자가 잃는 정보가 있는지 검토하고, 없으면 삭제한다. 튜토리얼이 아닌 글에서는 특히 다음 항목을 확인한다.

- **내부 구현값**: 설정 키, 변환 옵션, 메타데이터 저장 방식, 일괄 처리 단위
  - 좋음: "Drive에서 녹음을 내려받아 WAV 파일로 변환합니다."
  - 나쁨: "녹음을 내려받아 ffmpeg로 16kHz 모노 WAV로 바꿉니다."
- **보호 장치의 세부**: 중복 방지 표식, 사용량 한도 수치, 재시도 규칙, 필터링 조건
- **부수적 정보**: 설명 없이 언급만 하는 다른 도구, 채널 이름, 대체(fallback) 모델, 논지와 무관한 공개일
- **현재 중단된 작업**: "~하게 한 적도 있습니다" 형태의 서술은 삭제하거나, 현재 수행 중인 유사한 작업에 통합한다.
- **논지와 무관한 단서**: "공식 지원 목록에는 없지만"과 같은 주의 문구
- **근거 없는 부정문**: "승인은 묻지 않습니다", "답장은 하지 않습니다"처럼 수행하지 않는 일을 나열한 문장

단, 재현에 필요한 버전과 날짜(6절)는 유지한다. 생략 대상은 독자가 재현하거나 판단하는 데 사용하지 않는 세부 사항이다.

### 소제목

- 본문 소제목은 `##` 부터 `###` 까지만 쓴다. 목차에는 `##`·`###` 만 보인다.
- 제목(`#`)은 frontmatter 의 `title` 이 맡는다.
- 그 절이 다루는 개념을 짧은 명사구로 쓴다. 한 제목에 주제는 하나만 둔다. 번호는 붙이지 않는다.
- 절차 소제목은 `~하기` 명사형으로 쓴다. 예: `## 마이그레이션 적용하기`
- 볼드만 있는 줄로 소제목을 흉내 내지 않는다.
  - 그 아래 문단이 둘 이상이면 `###` 로 올린다.
  - 하나뿐이면 소제목 없이 그 문단 첫 문장만 굵게 한다.
- `##` 아래 `###` 가 하나뿐이면 그 `###` 를 걷어낸다.
- 은솔이 직접 지정한 소제목은 위 형식과 다르더라도 그대로 사용한다. 예: `## 도구를 만들자!`

### 조사기

직접 겪은 장애나 성능 문제를 추적한 글이다.

- 문제 → 관찰 → 가설 → 실험 → 결과 → 원리 → 결정 순서로 쓴다.
- 원리 설명은 결과 다음에 둔다. 독자가 왜 그런지 궁금해진 뒤에 푼다.
- 틀린 가설도 지우지 않고 왜 틀렸는지 쓴다.
- 첫 가설이 바로 맞았으면 문제 → 원인 → 조치로 짧게 쓴다.

### 결론

- 에세이형: `## 글을 마치며` → 요약 → 의견 → 독자에게 던지는 질문 → `:::see-also`
  - 의견은 은솔이 말한 것만 쓴다. 없으면 은솔에게 묻는다.
  - `:::see-also` 는 참고한 출처가 있을 때만 둔다.
- 튜토리얼: 마지막 단계에서 끝내도 된다.
- 조사기: 결정에서 무엇을 바꿨고 무엇이 남았는지 쓰고 끝낸다.

## 3. 표기

- 용어
  - 제품명은 공식 표기를 대소문자까지 그대로 쓴다. 예: Cloudflare Workers, TanStack Start, Homebrew, GitHub, macOS
  - 일반 개념은 음차로 쓴다. 예: 캐시, 마이그레이션, 프리렌더
  - 한 개념은 제목·설명·태그·본문에서 같은 표기로 쓴다.
  - 공식 이름이 있으면 그 이름을 쓴다. 정의 없이 새 용어를 만들지 않는다.
  - 독자에게 생소한 개발 용어는 일상어로 바꾸고, 해당 용어가 반드시 필요한 경우에만 `:term` 을 단다.
    - 예: "엔티티" → 누적된 기록은 "맥락", 분류 단위는 "사람·회사·프로젝트"
  - 한 표현이 명사와 동사구로 모두 읽힐 수 있으면 의미가 드러나도록 풀어 쓴다.
    - 예: "할 일"을 TODO의 의미로 쓰는 글에서 "제가 할 일, 제가 갈 일정" → "제가 해야 하는 일, 제가 가야 하는 일정"
- 인라인 코드는 코드나 터미널에 그대로 치는 것에 쓴다.
  - 명령어, API·함수 이름, 파일 경로, 설정 키, 환경 변수, 값
  - 예: `pnpm build`, `crypto.subtle.deriveBits`, `wrangler.jsonc`, `DEV_OWNER=1`
  - 제품명과 일반 단어는 감싸지 않는다.
- 코드 블록
  - 언어 태그를 붙인다.
  - 블록 앞에 목적을 한 문장으로 쓴다.
  - 주석과 예시 값은 한국어로 쓴다.
- 터미널 명령
  - 명령 앞에 `$` 같은 프롬프트 기호를 붙이지 않는다. 복사해서 바로 실행할 수 있게 한다.
  - 출력은 명령과 다른 블록(`text`)에 둔다.
  - 긴 출력은 필요한 줄만 남기고, 뺀 자리에 `...` 를 둔다.
- 볼드
  - 강조는 볼드로 한다.
  - 볼드는 문장 전체가 아니라 강조할 구절에만 건다. 접속사나 종결 어미는 볼드 밖에 둔다.
    - 좋음: "이 통화는 **모두 전사록과 함께 데이터베이스에 저장되어 있어서**, 지난 통화도 다시 찾아 읽습니다."
    - 나쁨: "그리고 **이 통화는 모두 전사록과 함께 데이터베이스에 저장되어 있습니다**."
  - 볼드가 괄호·따옴표·마침표로 끝나면 바로 뒤에 글자를 붙이지 않는다. 붙이면 볼드가 풀리고 `**` 가 글자로 보인다. 구두점을 볼드 밖으로 빼거나 문장을 바꾼다.
    - 좋음: `**설정**(config)에서`
    - 나쁨: `**설정(config)**에서`
- 목록
  - 리스트를 적극적으로 쓴다.
  - 예시를 나열하는 목록은 각 항목을 연결 어미로 이어 하나의 문장처럼 읽히도록 구성할 수 있다. 이 경우 마지막 항목에만 마침표를 찍는다.

    ```md
    - 번개장터와 당근마켓에서 중고 매물을 찾아 원하는 매물이 나왔는지 보고하거나,
    - 지도 API를 사용해서 목적지까지 가는 시간과 경로를 계산해주기도 하고,
    - Mac에 직접 접근하여 Apple Music으로 음악을 틀게 하기도 합니다.
    ```
  - 순서를 바꾸면 뜻이 달라지는 절차는 번호 목록(`1.`)으로 쓰고, 한 단계에 한 동작만 둔다. 나머지는 `-` 로 쓴다.
  - 라벨을 붙인 항목은 `- **라벨**: 설명` 꼴로 쓴다. 콜론은 볼드 밖에 둔다.
  - 항목 설명이 두 문장을 넘으면 문단으로 쓴다.
- 표는 값을 나란히 비교할 때 쓴다. 판단과 이유는 표 밖 문장으로 쓴다.
- UI 경로는 대괄호와 `->` 로 쓰고 코드로 감싸지 않는다. 예: [설정] -> [도메인]
- 화면에 나오는 문구는 큰따옴표로 감싼다. 예: "HuggingFace에서 검색" 섹션
- 숫자와 단위는 붙여 쓴다. 예: 128.9KB, 10ms, 390px
- 링크
  - 링크 텍스트는 대상의 이름 또는 해당 출처가 뒷받침하는 구절로 한다. "여기", "이 링크"는 쓰지 않는다.
    - 좋음: [Paraglide JS 문서](https://inlang.com/m/gerre34r/library-inlang-paraglideJs)에 나옵니다.
    - 좋음: Structured는 [MCP 서버를 직접 제공](https://structured.app/blog/structured-mcp)합니다.
    - 나쁨: 자세한 내용은 [여기](https://inlang.com/m/gerre34r/library-inlang-paraglideJs)를 보세요.
  - 같은 주소는 본문에서 처음 나올 때만 링크한다.
  - 다른 글을 전제할 때도 링크만 걸지 않는다. 필요한 만큼 본문에 요약한다.
- 이미지
  - 대체 텍스트에는 그림이 보여 주는 것을 쓴다. 예: "글 목록 화면"
  - 그림 안의 글자(라벨·범례)에는 1인칭을 쓰지 않는다. 1인칭은 본문과 캡션에서만 쓴다.
  - 그림 안에 한국어 글자가 있으면 영어판 그림을 `<이름>.en.svg` 로 같은 폴더에 둔다. 번역 구조 검사는 언어 접미사를 뺀 경로로 비교한다.
    - 좋음: "직접 만든 프로그램"
    - 나쁨: "제가 만든 프로그램"
  - 캡션에는 그림에서 볼 점을 쓴다. 예: "위쪽 태그로 글을 거를 수 있습니다"
  - 남이 만든 그림은 라이선스를 확인하고 캡션에 출처와 라이선스를 적는다. 라이선스를 모르면 그림 대신 링크를 건다.
  - 외부 주소(`https://…`)의 이미지는 쓰지 않는다. 보안 정책(CSP)이 막아서 독자에게 안 보인다. 파일을 글 폴더에 둔다(`pnpm content:check` 가 잡는다).

## 4. 맞춤법 (표준으로 교정한다)

교정하는 것:

| 틀림 | 맞음 |
|---|---|
| 이였다 | 이었다 |
| 할수 있다 | 할 수 있다 |
| 하는것 | 하는 것 |
| 하는김에 | 하는 김에 |
| 시작 해줍니다 | 시작해줍니다 |
| oMLX 를 | oMLX를 (영문·코드 뒤 조사는 붙인다) |

- 보조용언은 붙여 쓴다. 예: 해줍니다, 해봅니다, 해둡니다, 묶다보니
- 명백한 오타도 고친다. 예: 프롬포트 → 프롬프트
- `pnpm content:check` 가 일부를 경고로 알려 준다: 영문·코드 뒤 띄어 쓴 조사, "할수", "하는것", "하는김에", 그리고 3절의 풀린 볼드. 나머지("이였다", "시작 해줍니다")는 기계로 가리기 어려워 직접 본다.

그대로 두는 것:

- 개발자 관용 외래어: 레포지토리, 어플리케이션 등
- 일부러 귀엽게 쓴 표기: 와자뵤, 연락처루 등

## 5. AI 문체 신호 걷어내기

글을 다 쓴 뒤 아래를 찾아서 고친다. 한 문장씩 보면 멀쩡한 경우가 많으니, 같은 신호가 글 전체에 몇 번 나오는지 세어 보고 잦을 때 고친다. 논지의 핵심을 맡은 문장은 남긴다.

| 신호 | 예 | 고치는 방향 |
|---|---|---|
| 빈 수사 | "혁신적인", "강력한", "완벽한" | 수치나 사실로 바꾸거나 뺀다 |
| 과한 접속사 | 문장마다 "또한", "따라서", "이처럼" | 대부분 뺀다. 흐름이 안 이어지면 문단 순서부터 본다. 역접의 "그러나"는 남긴다(2절) |
| "~할 수 있습니다" 남발 | "확인할 수 있습니다", "사용할 수 있습니다" | "확인합니다", "씁니다" |
| 같은 문장 틀 반복 | "~는 ~입니다." 가 연달아 | 문장 길이와 시작을 바꾼다. 같은 서술어로 끝나는 조건이 셋 이상 이어지면 목록으로 바꾼다 |
| 번역투 | "~를 가지고 있다", "~에 대해서", "~하는 것이 가능하다" | "~가 있다", "~를", "~할 수 있다" |
| 명사화·피동 | "검토를 진행했습니다", "변경이 이루어졌습니다" | "검토했습니다", "바꿨습니다" |
| 문어 한자어 | "상기", "금번", "~에 기반하여" | "위", "이번", "~를 바탕으로" |
| 부정 뒤 긍정 반복 | "A가 아니라 B입니다" 가 글에 여러 번 | 핵심 대비 하나만 남기고 평서문으로 |
| 극적 예고 | "답은 간단합니다.", "핵심은 이것입니다." | 예고를 빼고 바로 말한다 |
| 강조 도치 | "이번에 고른 것이 D1입니다" | "이번에는 D1을 골랐습니다" |
| 평가 부사 | "정확히", "당연히", "확실히" | 뺀다 |
| 서술어 없는 문장 | 본문 문단의 "빠른 빌드, 작은 번들." | 문장으로 끝맺는다(목록 항목은 괜찮다) |
| 문장을 잇는 줄표 | "빌드가 끝나면 — 배포합니다" | 문장을 나누거나 쉼표로 잇는다(화살표 `->`, `→` 는 괜찮다) |
| 작업 흔적 | "(초안에 없던 내용)", "(직접 확인하지 못함)" | 지운다. 독자가 알아야 할 한계면 본문 문장으로 쓴다 |
| 없던 주장 | 근거 없는 "많은 개발자가" | 근거를 대거나 뺀다 |
| 장식용 마무리 | "앞으로가 기대됩니다" | 실제 다음 할 일이나 질문으로 |

## 6. 사람과 AI 가 믿기 쉬운 글

- 1차 경험을 쓴다: 실제로 해 본 것, 실제로 본 오류 메시지.
- 예시·로그·API 이름은 실제로 있는 것만 쓴다. 그럴듯하게 지어낸 예시는 쓰지 않는다.
- 재현 조건을 적는다: 버전, 날짜, 환경.
  - 성능·크기 수치에는 잰 도구, 버전, 날짜를 붙인다.
- "최근", "현재", "올해", "최신 버전"처럼 쓴 때에 기대는 말 대신 날짜와 버전 번호를 쓴다. 글은 남고 "최근"은 금방 틀린 말이 된다.
  - 좋음: "2026년 10월 기준 TanStack Start 1.169에서는"
  - 나쁨: "최신 버전에서는"
- 1차 출처에 링크한다: 공식 문서, 저장소, 이슈.
- 고른 것만 쓰지 않고, 검토하고 버린 대안과 고른 이유를 쓴다.
- 확인한 사실, 거기서 끌어낸 추론, 의견을 독자가 구분할 수 있게 쓴다. 의견은 은솔이 말한 것만 쓴다.
- "~것 같습니다"는 정말 모를 때만 쓴다. 확인할 수 있는 것이면 확인하고 단정한다.
- 글의 흐름을 잇기 위해 새로 지어 넣는 문장(전환, 요약, 부연)도 같은 기준으로 확인한다. 다듬는 과정에서 더해진 문장은 초고보다 확인을 거치지 않았을 가능성이 높다.
- 틀린 문장은 그 자리에서 고친다. 뒤에 괄호로 "참고로 ~"를 덧붙여 덮지 않는다.
- 예전 작업을 쓸 때는 지금도 그 상태인지 다시 확인한다. 고쳤다고 쓰기 전에 지금도 고쳐져 있는지 본다.
- 글을 쓴 목적과 독자가 얻는 것을 첫 섹션(정의 다음 문단)에 밝힌다.
- 은솔의 사용 방식은 파일이나 설정에서 추론하여 쓰지 않는다. 스킬이나 설정이 존재한다는 사실만으로 "이렇게 사용합니다"라고 서술하지 않으며, 반드시 은솔에게 확인한다.
- 보안 설정(실행 승인 비활성화, 권한 범위 등)을 드러내는 문장은 은솔의 확인을 받은 뒤에만 쓴다.

## 7. 검색 (SEO)

- 제목
  - 검색할 말을 앞쪽에 둔다.
  - 공유 카드(OG 이미지)에서는 공백 포함 40자 안팎까지 가장 큰 글씨로 나온다. 더 길면 글씨가 작아지고, 70자를 넘으면 잘린다.
- 설명(`description`)
  - 160자 이하이고, 글이 답하는 질문을 담는다.
  - 검색 결과, 글 목록, 링크 공유 미리보기에 보인다.
- 소제목은 목차와 검색 결과에 그대로 보인다. 내용을 짐작할 수 있게 쓴다.
- 태그는 `content/tags.yaml` 에 있는 것을 먼저 쓴다. 새 태그는 표시 이름(ko·en)을 같이 넣는다.

## 8. 본문 문법

Markdown 에 더해 아래 문법을 쓸 수 있다. 원본 HTML 태그는 쓸 수 없고, 모르는 디렉티브는 빌드 오류다.

링크, `:term`, `:::details` 를 하나도 열지 않아도 본문만으로 글이 읽혀야 한다. 이 문법들은 더 알고 싶은 독자를 위한 것이고, 핵심 설명을 대신하지 않는다.

| 문법 | 쓰는 때 |
|---|---|
| `> [!NOTE]` 참고 | 본문 흐름 밖의 덧붙임 정보 |
| `> [!TIP]` 팁 | 알면 편한 방법, 지름길 |
| `> [!IMPORTANT]` 중요 | 놓치면 다음 단계가 안 되는 것 |
| `> [!WARNING]` 주의 | 실수하기 쉬운 것 |
| `> [!CAUTION]` 경고 | 데이터 손실, 보안처럼 되돌리기 어려운 것 |
| `:::details` | 읽지 않아도 글이 이어지는 부가 설명. 첫 문단이 접힌 상태의 요약 줄이다 |
| `:::see-also` | 참고한 출처 전체 목록. 본문에서 링크한 출처도 넣는다. 항목 앞에 표지를 붙인다 |
| `::::quote` + `:::translation` / `:::original` | 외국어 원문 인용. 표현 자체가 필요할 때만 쓰고, 사실만 필요하면 링크를 걸고 풀어 쓴다. 한국어 페이지는 번역과 원문을 같이, 영어 페이지는 원문만 보여 준다 |
| `:term[라벨]{key="..."}` | 독자가 모를 수 있는 개념. 그 절을 이해하는 데 필요한 말에만, 글에서 처음 나올 때 한 번 단다. 소제목·표·`:::see-also` 안에는 달지 않는다. 정의는 `content/glossary.yaml` 에 둔다 |
| `:::widget-<이름>` | 글 안에서 직접 눌러 볼 예시. 등록된 위젯만 쓴다(`src/features/embeds/config/names.ts`) |

`:::details` 는 첫 문단을 요약 줄로 쓴다.

```md
:::details
빌드할 때 하는 일

- 폴더 이름이 날짜와 같은지 확인합니다.
:::
```

`:::see-also` 표지는 `[paper]`, `[docs]`, `[repo]`, `[article]` 넷이다.

```md
:::see-also
- [docs] [TanStack Start](https://tanstack.com/start)
- [repo] [Content Collections](https://github.com/sdorra/content-collections)
:::
```

인용은 두 개가 붙지 않게 사이에 은솔의 문단을 둔다. `:::original` 안의 글자는 원문 그대로 둔다.

```md
::::quote
:::translation
단순함은 신뢰성의 전제 조건이다.
:::
:::original
Simplicity is prerequisite for reliability.
:::
::::
```

`:::widget-<이름>` 블록 안의 글은 위젯을 띄울 수 없을 때 대신 보인다.
